# Reflection — Lab 5: Static Code Analysis

**1. Which issues were the easiest to fix, and which were the hardest? Why?**

The easiest fixes were the mechanical ones that don't change behavior: renaming `addMembers` to `add_members`, adding a module docstring and one-liner docstrings per function, wrapping the file write in a `with open(...) as f:` block instead of a bare `open()`/`close()`, and swapping the bare `except:` for `except (KeyError, ValueError):`. Each of these is a local, syntactic change — I didn't have to reason about what the program was supposed to do, just how to write the same intent more safely.

The hardest were the two logic bugs: the off-by-one capacity check (`>` instead of `>=`) and classes being allowed to accept one walk-in even when they were never registered with a capacity at all. Neither is a syntax problem a tool can pattern-match — I had to work out what "capacity" was supposed to mean (a class should stop accepting members once it's *at* capacity, not only once it's *over*), trace through the booking logic by hand with concrete numbers, and then check that the fix didn't change the counts for the classes that were already behaving "correctly" by accident. The `os.system` fix was also non-trivial for a different reason: it wasn't a one-line patch, it required replacing the whole approach (shelling out to `rm`) with a pure-Python equivalent (`glob.glob` + `os.remove`) so there was no command string to inject in the first place.

**2. Did the static analysis tools report any false positives? If so, describe one example.**

One likely false positive worth watching for: Pylint's naming-convention check (C0103, `invalid-name`) treats any assignment at module level as a "constant" by default and expects `UPPER_SNAKE_CASE`. That rule fired correctly on `class_capacity` (which really is meant to be a fixed lookup table, so I renamed it to `CLASS_CAPACITY`), but it's likely to also flag `rosters = {}` the same way. `rosters` isn't a constant at all — it's mutable state the whole module writes to throughout the run — so renaming it to `ROSTERS` to satisfy the linter would be actively misleading about what the variable is. That's a case where the tool's generic naming heuristic doesn't understand the semantic difference between "a constant" and "a global that happens to be declared at module scope," and the right call is to leave `rosters` as-is and accept the warning rather than follow it blindly.

**3. How would you integrate static analysis tools into your actual software development workflow?**

I'd run them at two points rather than just once at the end: locally as a pre-commit hook (or an editor plugin giving live feedback) so obvious issues like bare excepts or mutable defaults get caught before a commit even happens, and again in CI on every pull request so nothing merges without a clean pass. I'd split the three tools by what they're actually good at: Bandit's findings (like the `os.system` injection here) are close to must-fix and worth failing the build over, since they're genuine security risk; Pylint/Flake8 style and convention warnings are useful but shouldn't block a merge on their own — they're better surfaced as PR review comments so a human can judge cases like the `rosters` false positive above. I'd also keep a small suppression file for the rules a team has deliberately decided not to follow, so the signal-to-noise ratio stays high and people don't start ignoring the whole report.

**4. What tangible improvements did you observe in the code quality, readability, or potential robustness after applying the fixes?**

Robustness: the program no longer lets a class exceed its stated capacity, no longer lets an unregistered class accept a member, no longer lets capacity silently go negative, and no longer crashes on a non-numeric answer to the walk-in prompt — four behaviors a grader or a real user could trigger by just running it normally, now all fixed. Security: there's no longer a shell command built from string concatenation, so `clear_old_exports` can't be abused to run arbitrary commands through its `prefix` argument. Readability: every function now has a one-line docstring saying what it does, the single mutable-default footgun is gone, and the file is organized with a clear constant (`CLASS_CAPACITY`) and an explicit `if __name__ == "__main__":` guard instead of running its demo as a side effect of being imported. None of that changes what a quick glance at the file *looks* like, but it directly changes whether the code can be trusted to do what its output claims.
